---

## Changes Made

### 1. Created the Customer Model

Created a `Customer` model to represent customer information in the application.

The model contains the following fields:
- Username
- Password
- Email
- Mobile Number
- Address

---

### Why Was This Needed?

A model defines the structure of data that will be stored in the database.

Each field in the model represents a column in the database table, while each customer record represents a row.

This model will be used to store and retrieve customer information.

---

### 2. Registered the Customer Model in Django Admin

Registered the `Customer` model in the Django Admin Panel.

---

### Why Was This Needed?

By default, Django Admin does not display custom models.

Registering the model makes it available in the Admin Panel, allowing administrators to:

- View customer records.
- Add new customers.
- Update existing customer details.
- Delete customer records.

No custom admin interface needs to be created because Django automatically generates one.

---

## What I Learned

- A **Model** defines the database structure.
- Each model is converted into a database table.
- Each field in the model becomes a column in the table.
- Each object created from the model becomes a row in the database.
- Models must be registered in `admin.py` to appear in the Django Admin Panel.
- Django Admin provides built-in CRUD (Create, Read, Update, Delete) operations for registered models.

---

# Database Migration

## Commands Used

```bash
python manage.py makemigrations
python manage.py migrate
```

---

## 1. Create Migration Files (`makemigrations`)

### Purpose

Generated migration files based on the changes made to the `Customer` model.

### Why Was This Needed?

After creating or modifying a model, Django needs instructions on how to update the database. The `makemigrations` command compares the current models with the previous state and generates migration files containing the required database operations.

### Result

- Created the migration file:
  - `feastoApp/migrations/0001_initial.py`
- Detected the creation of the `Customer` model.

---

## 2. Apply Migrations (`migrate`)

### Purpose

Applied all pending migrations to the database.

### Why Was This Needed?

Migration files only describe the changes. The `migrate` command executes those changes and creates or updates the actual database tables.

### Result

- Created the `Customer` table in the database.
- Applied all pending migrations, including Django's built-in apps (`admin`, `auth`, `contenttypes`, `sessions`) and the custom `feastoApp`.

---

## What I Learned

- `makemigrations` creates migration files based on model changes.
- `migrate` applies those migration files to the database.
- Migration files act as a blueprint for database changes.
- The database is not updated until the `migrate` command is executed.

---

## Workflow

```
Create/Modify Model
        ↓
python manage.py makemigrations
        ↓
Migration File Created
        ↓
python manage.py migrate
        ↓
Database Table Created/Updated
```
---

## One-Line Summary

Generated migration files for the `Customer` model and applied them to create the corresponding database table.

# User Registration & Authentication

## Files Modified
- `feastoApp/views.py`
- `feastoApp/urls.py`
- `templates/signin.html`
- `templates/admin_home.html`
- `templates/customer_home.html`

---

## Changes Made

### 1. Implemented User Registration

Created the registration logic to:
- Receive user details from the Sign Up form.
- Check whether the username already exists.
- Prevent duplicate usernames.
- Create a new customer if the username is unique.
- Redirect the user to the Sign In page after successful registration.

### Why Was This Needed?

Every user should have a unique username. Checking for duplicate usernames prevents multiple accounts with the same identity and ensures data consistency.

---

### 2. Implemented User Authentication

Created the Sign In logic to:
- Receive the username and password entered by the user.
- Verify the credentials against the Customer records stored in the database.
- Authenticate only registered users.

### Why Was This Needed?

Authentication ensures that only valid users can access the application.

---

### 3. Implemented Role-Based Navigation

After successful authentication:

- If the username is **admin**, redirect to the **Admin Home** page.
- Otherwise, redirect to the **Customer Home** page.

### Why Was This Needed?

Different users have different responsibilities. The administrator manages the application, while customers use the application's services.

---

### 4. Implemented Login Failure Handling

If the entered username or password does not match any customer record, redirect the user to a **Sign In Failed** page.

### Why Was This Needed?

Provides feedback to the user when authentication fails instead of leaving them on the same page.

---

### 5. Configured URL Routing

Added a URL route for the Sign In functionality.

### Why Was This Needed?

Allows the Sign In form to send user credentials to the authentication logic.

---

## What I Learned

- User registration involves validating data before saving it.
- Duplicate usernames should not be allowed.
- Authentication verifies user credentials using database records.
- Different users can be redirected to different pages based on their role.
- Exception handling is useful for managing invalid login attempts.
- URL routing connects browser requests to view functions.

---
